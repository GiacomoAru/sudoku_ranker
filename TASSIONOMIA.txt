# Tassonomia implementabile delle tecniche di risoluzione del Sudoku

## Sintesi esecutiva

Non esiste una tassonomia universale e definitivamente “esaustiva” delle tecniche Sudoku. Sudoku Explainer stesso osserva che tecniche diverse possono essere casi particolari della stessa inferenza, che alcune classificazioni producono più o meno nomi a parità di semantica e che la terminologia delle tecniche avanzate non è standardizzata tra i solver. Il catalogo proposto adotta quindi un perimetro preciso: **Sudoku classico 9×9, tecniche umane documentate ufficialmente da HoDoKu, famiglie di Sudoku Explainer 1.2.1 e relative estensioni di SukakuExplainer, più il fallback progettuale Complete Forcing Tree**. Sono escluse le varianti Sudoku, i pattern esotici privi di nomenclatura stabile e i metodi puramente matematici non destinati a produrre spiegazioni umane. citeturn12view1turn8search5

Le decisioni architetturali principali sono:

| Decisione | Regola proposta |
|---|---|
| Nome canonico | Nome inglese più diffuso nei solver, con descrizione italiana e alias registrati |
| Valore `se` | Rating pubblicato da Sudoku Explainer o SukakuExplainer |
| Valore `pseudo_se` | Valore progettuale interpolato sulla scala SE, esplicitamente non ufficiale |
| Valore `project` | Valore interno per tecniche non confrontabili direttamente con SE |
| Tecniche specifiche | Prevalgono sui nomi generici quando il rilevatore ha verificato tutta la struttura |
| Tecniche generiche | Restano come parent astratti o fallback di classificazione |
| Nested | Una catena contiene inferenze giustificate da sottocatene |
| Complete Forcing Tree | Albero esaustivo di contraddizione, separato dalle Nested |
| Fallback | `0 = ordinary`, `1 = nested`, `2 = complete_tree` |
| Difficoltà | `base_difficulty + proof_complexity_extra`, conservando separatamente i due valori |

La scala ufficiale SE 1.2.1 costituisce l’ancora numerica: da 1.0 per Last Value a 6.2 per Aligned Pair Exclusion, da 6.5 in poi per cicli e catene, da 8.5 per Dynamic Forcing Chains, da 9.0 per Dynamic Forcing Chains Plus e oltre 9.5 per Nested Forcing Chains. SukakuExplainer ha poi introdotto intervalli per Skyscraper, Two-String Kite, Turbot Crane, generalized wings e livelli Nested più profondi. citeturn13view0turn14view0

Nel solver allegato, la separazione tra tecniche ordinarie e Nested è già presente, ma dipende da nomi e metadata dei runner. Il calcolo della difficoltà usa metriche strutturali e una crescita logaritmica. fileciteturn0file0 L’attuale `Nested Forcing Chain`, tuttavia, chiama `_CompleteNestedSearch`, che esplora ricorsivamente tutte le alternative senza limiti interni di profondità, nodi o rami. Questa procedura deve diventare `Complete Forcing Tree`. fileciteturn0file1 Inoltre, `techniques.py` ricostruisce le metriche dalla sola rappresentazione visualizzata, usa `nesting_depth` invece di `nested_depth` e sostituisce le metriche complete prodotte dal motore. Questo è l’errore prioritario della pipeline. fileciteturn0file2

La priorità finale raccomandata è:

| Ordine | Famiglie |
|---:|---|
| Primo | Singles, Direct, intersections, subsets |
| Secondo | Basic fish, single-digit patterns, coloring, wings |
| Terzo | Uniqueness, Sue de Coq, exclusion, complex fish |
| Quarto | Bivalue chains, AIC, grouped chains, ALS |
| Quinto | Multiple, dynamic e advanced forcing, templates, Kraken, nets |
| Sesto | Vere Nested Forcing Chains |
| Ultimo | Complete Forcing Tree |

## Fondamenti formali e architettura del motore

Si assuma uno stato Sudoku composto da:

```text
Grid[r,c]                  valore risolto oppure 0
Candidates[r,c]            insieme dei candidati ancora possibili
Units                      9 righe + 9 colonne + 9 box
Peers[r,c]                 celle che condividono almeno una casa
Candidate                  (row, column, digit)
Literal                    (row, column, digit, state)
```

Un **weak link** tra due candidati significa che non possono essere entrambi veri. Un **strong link** significa che, se uno è falso, l’altro deve essere vero. Una AIC alterna strong e weak link; una catena reversibile può essere letta in entrambi i sensi. HoDoKu distingue inoltre i group link, nei quali un nodo rappresenta più candidati equivalenti, e le forcing net, nelle quali un’inferenza dipende da più predecessori o il ragionamento si ramifica e riconverge. citeturn0search0

Un ALS è un insieme di `N` celle appartenenti a una casa che contiene complessivamente `N+1` candidati. Due ALS sono collegabili tramite un Restricted Common Candidate, RCC, quando tutte le occorrenze di quel candidato nei due ALS si vedono reciprocamente. citeturn7search2

Un fish è rappresentabile come un problema di incidenza tra **base sets** e **cover sets** per una singola cifra. X-Wing, Swordfish e Jellyfish hanno rispettivamente dimensione 2, 3 e 4. Un Franken Fish usa almeno un box tra base o cover; un Mutant Fish combina tutti i tipi di casa; fins, endo-fins e cannibalismo sono proprietà strutturali del fish, non semplici differenze nel numero di candidati. citeturn1search4turn1search1turn1search3

Le strutture minime consigliate sono:

```python
from dataclasses import dataclass, field
from enum import Enum
from typing import Any, Mapping, Sequence


Candidate = tuple[int, int, int]


@dataclass(frozen=True, slots=True)
class Literal:
    row: int
    column: int
    digit: int
    state: bool


@dataclass(frozen=True, slots=True)
class GroupNode:
    digit: int
    cells: frozenset[tuple[int, int]]
    house_ids: tuple[int, ...]
    role: str
    # Esempi: "row-segment", "column-segment", "box-segment"


@dataclass(frozen=True, slots=True)
class ALS:
    id: int
    house_id: int
    cells: frozenset[tuple[int, int]]
    candidates: frozenset[int]

    def validate(self) -> None:
        if len(self.candidates) != len(self.cells) + 1:
            raise ValueError("Un ALS deve avere N celle e N+1 candidati.")


@dataclass(frozen=True, slots=True)
class RCC:
    digit: int
    left_als_id: int
    right_als_id: int
    left_occurrences: frozenset[tuple[int, int]]
    right_occurrences: frozenset[tuple[int, int]]


@dataclass(slots=True)
class ProofNode:
    id: int
    kind: str
    conclusion: Literal | None
    parents: tuple[int, ...]
    reason: str
    depth: int
    payload: Mapping[str, Any] = field(default_factory=dict)


@dataclass(slots=True)
class ProofDAG:
    nodes: dict[int, ProofNode]
    roots: tuple[int, ...]
    conclusions: tuple[int, ...]
    nested_proofs: dict[int, "ProofDAG"] = field(default_factory=dict)
```

Il DAG deve essere la fonte autorevole della prova. Le liste lineari di candidati utilizzate dall’interfaccia devono essere viste renderizzate del DAG, non la fonte da cui ricostruire la complessità.

```mermaid
flowchart TD
    A[Assunzione principale] --> B[Inferenza statica]
    B --> C[Inferenza dinamica]
    C --> D{Inferenza non direttamente disponibile}
    D -->|sottoprova| N1[Assunzione della Nested]
    N1 --> N2[Catena interna]
    N2 --> N3[Conclusione della sottoprova]
    N3 --> E[Inferenza giustificata nella catena principale]
    D -->|regola diretta| E
    E --> F[Conclusione finale]
    C --> G[Ramo alternativo]
    G --> F
```

Questo modello corrisponde alla semantica delle Nested di Sudoku Explainer: un potenziale della catena principale può contenere una `nestedChain`; le catene annidate vengono raccolte ricorsivamente, la loro complessità viene sommata e operano su uno stato che include le eliminazioni già prodotte dalla catena contenitore. Non è quindi necessario risolvere esaustivamente l’intero Sudoku per produrre una Nested. citeturn12view0

Il flusso del solver deve invece essere:

```mermaid
flowchart TD
    S[Stato Sudoku] --> O[Runner ordinary ordinati per difficoltà]
    O --> Q{Esiste una mossa ordinary?}
    Q -->|Sì| R[Deduplica, classifica e ordina]
    R --> A[Applica la mossa più semplice]
    Q -->|No| N[Motore Nested con budget]
    N --> NQ{Esiste una vera Nested?}
    NQ -->|Sì| NR[Valuta ProofDAG Nested]
    NR --> A
    NQ -->|No| C[Complete Forcing Tree]
    C --> CQ{Esiste una contraddizione completa?}
    CQ -->|Sì| CR[Restituisce una sola conclusione estrema]
    CR --> A
    CQ -->|No| X[Stuck o solver esterno]
    A --> S
```

Il fallback non deve essere dedotto dal nome del runner. Deve provenire direttamente dal catalogo:

```python
ordinary = entry.fallback_tier == 0
nested = entry.fallback_tier == 1
complete_tree = entry.fallback_tier == 2
```

## Algoritmi di rilevamento e pseudocodice

Ogni detector deve restituire conclusioni indipendenti dalla soluzione completa:

```python
@dataclass(frozen=True)
class Deduction:
    technique_id: str
    placements: tuple[Candidate, ...]
    eliminations: tuple[Candidate, ...]
    proof: ProofDAG
    metrics: Mapping[str, int | float]
    pattern: Mapping[str, object]

    def validate_nonempty(self) -> None:
        if not self.placements and not self.eliminations:
            raise ValueError("Una deduzione deve modificare lo stato.")
```

Il motore può usare la soluzione completa soltanto nei test di soundness o in strumenti separati, mai per costruire la prova logica.

**Subsets e intersezioni**

```python
def find_naked_subset(state, size):
    for house in state.houses:
        eligible = [
            cell for cell in house.unsolved_cells
            if 2 <= len(state.candidates[cell]) <= size
        ]

        for cells in combinations(eligible, size):
            digits = union(state.candidates[cell] for cell in cells)

            if len(digits) != size:
                continue

            eliminations = {
                (cell, digit)
                for cell in house.unsolved_cells - set(cells)
                for digit in digits & state.candidates[cell]
            }

            if eliminations:
                yield build_local_deduction(
                    technique_id=f"subset.naked.{size}",
                    support=cells,
                    eliminations=eliminations,
                )
```

Per evitare duplicati e tecniche ridondanti, il detector deve canonicalizzare `(house_id, cells, digits)` e rifiutare le forme che hanno un equivalente obbligatoriamente più semplice nella stessa casa.

```python
def find_fish(state, digit, size, allowed_base_types, allowed_cover_types):
    base_sets = candidate_houses(
        state,
        digit,
        house_types=allowed_base_types,

    for selected_bases in combinations(base_sets, size):
```

**AIC, Nice Loops e group nodes**

Il grafo di implicazione non dovrebbe contenere soltanto archi genericamente etichettati `x`, `y` o `peer`. Ogni arco deve dichiarare polarità, forza e supporto:

```python
class ImplicationEdge:

    target_id: int
    link_strength: str       # "strong" oppure "weak"
    reason: str              # "peer", "bivalue", "conjugate", "group", "rcc"
    support_candidates: tuple[Candidate, ...]
```

Pseudocodice:

```python
def enumerate_aic(graph, limits):
    for start in graph.nodes:
        stack = [(start, [], None)]

        while stack:
            current, path, expected_strength = stack.pop()

            if len(path) >= limits.max_edges:
                continue

            for edge in graph.outgoing(current):
                if expected_strength and edge.link_strength != expected_strength:
                    continue

                if violates_simple_path(path, edge):
                    continue

                new_path = path + [edge]

                conclusion = classify_aic_closure(start, edge.target_id, new_path)

                if conclusion:
                    yield conclusion.with_proof(path_to_dag(new_path))

                stack.append((
                    edge.target_id,
                    new_path,
                    opposite_strength(edge.link_strength),
                ))
```

**ALS e grafo RCC**

```python
def enumerate_als(state, max_cells=6):
    seen = set()

    for house in state.houses:
        cells = house.unsolved_cells

        for size in range(1, min(max_cells, len(cells)) + 1):
            for subset in combinations(cells, size):
                digits = union(state.candidates[cell] for cell in subset)

                if len(digits) != size + 1:
                    continue

                signature = canonical_als_signature(subset, digits)

                if signature in seen:
                    continue

                seen.add(signature)
                yield ALS(
                    id=stable_id(signature),
                    house_id=house.id,
                    cells=frozenset(subset),
                    candidates=frozenset(digits),
                )


def restricted_common_candidates(left, right, state):
    for digit in left.candidates & right.candidates:
        left_cells = occurrences_in_als(left, digit)
        right_cells = occurrences_in_als(right, digit)

        if all(sees(a, b) for a in left_cells for b in right_cells):
            yield RCC(
                digit=digit,
                left_als_id=left.id,
                right_als_id=right.id,
                left_occurrences=frozenset(left_cells),
                right_occurrences=frozenset(right_cells),
            )
```

Per ALS-XZ è sufficiente una coppia di ALS. Per ALS Chain si cerca un cammino nel grafo ALS-RCC, vietando RCC adiacenti uguali e controllando esplicitamente gli overlap. HoDoKu ammette overlap ALS in alcune costruzioni, incluso Death Blossom, purché la logica degli RCC rimanga valida. citeturn7search2

**Forcing chain e forcing net**

```python
def propagate_assumption(state, assumption, rule_profile):
    dag = ProofDAG(...)
    queue = [assumption]

    while queue:
        literal = queue.pop()

        for inference in rule_profile.inferences(state, literal, dag):
            if dag.contains_opposite(inference.conclusion):
                return Contradiction(dag, inference)

            if dag.add_if_new(inference):
                queue.append(inference.conclusion)

    return Propagation(dag)
```

La differenza tra chain e net non deve dipendere dal nome del runner:

```python
def classify_dependency_shape(proof):
    if any(len(node.parents) > 1 for node in proof.nodes.values()):
        return "net"

    if proof_has_fork_and_merge(proof):
        return "net"

    return "chain"
```

**Vera Nested Forcing Chain**

```python
@dataclass(frozen=True)
class NestedBudget:
    max_depth: int = 2
    max_nodes: int = 512
    max_branches: int = 64
    max_subproofs: int = 32
    max_results: int = 2


def prove_nested_inference(
    state,
    context_assumptions,
    target,
    *,
    remaining_depth,
    budget,
    memo,
    active,
):
    direct = prove_with_current_profile(
        state,
        context_assumptions,
        target,
        budget=budget,
    )

    if direct:
        return direct

    if remaining_depth <= 0:
        return None

    key = nested_cache_key(
        state,
        context_assumptions,
        target,
        remaining_depth,
    )

    if key in memo:
        return memo[key]

    if key in active:
        return None

    active.add(key)

    for split in bounded_logical_splits(state):
        branch_proofs = []

        for assumption in split.assumptions:
            child = prove_nested_inference(
                state,
                context_assumptions + (assumption,),
                target,
                remaining_depth=remaining_depth - 1,
                budget=budget,
                memo=memo,
                active=active,
            )

            if child is None:
                break

            branch_proofs.append(child)
        else:
            proof = attach_nested_subproofs(
                split,
                branch_proofs,
                target,
            )
            memo[key] = proof
            active.remove(key)
            return proof

    active.remove(key)
    memo[key] = None
    return None
```

La sottoprova deve dimostrare una singola inferenza utilizzata dalla catena contenitore. Non deve continuare arbitrariamente fino alla soluzione completa.

**Complete Forcing Tree**

```python
def complete_forcing_tree(state, root_assumption, limits):
    root_state = apply_assumption(state, root_assumption)

    result = prove_unsatisfiable_exhaustively(
        root_state,
        choose_branch="minimum_remaining_values",
        memoize=True,
        limits=limits,
    )

    if result.status == "unsatisfiable":
        return eliminate_opposite_of(root_assumption, proof=result.tree)

    return None
```

Per preservare il comportamento attuale si possono inizialmente mantenere limiti molto alti o configurabili. Il nome e il rating devono però dichiarare che si tratta di ricerca completa, non di una Nested canonica.

## Scala pseudo-SE e procedura di calibrazione

La scala proposta conserva come punti fissi i valori ufficiali SE e SukakuExplainer. I valori moderni non ufficiali vengono collocati per interpolazione tra tecniche di struttura comparabile. SE stesso dichiara che il proprio rating non è perfetto e adotta una strategia greedy basata sulla tecnica disponibile più semplice. citeturn13view0

| Fascia | Interpretazione progettuale |
|---:|---|
| 1.0-2.5 | Tecniche elementari e direct |
| 2.6-4.4 | Intersezioni, subsets, basic fish, pattern intermedi |
| 4.5-6.4 | Uniqueness, coloring, complex fish, generalized wings, ALS locali |
| 6.5-7.9 | AIC, Nice Loops, grouped chains, exclusion avanzata |
| 8.0-8.7 | Multiple forcing, templates, Kraken |
| 8.8-9.4 | Dynamic forcing, Plus iniziali, forcing nets |
| 9.5-12.9 | Nested Forcing Chains e livelli annidati crescenti |
| 13.0+ | Complete Forcing Tree |
| 99.0 | Ricerca non spiegabile, esclusa dal rating umano |

Il record pubblico deve sempre separare:

```python
{
    "base_difficulty": 9.6,
    "proof_complexity_extra": 0.4,
    "technical_difficulty": 10.0,
    "rating_kind": "pseudo_se",
    "difficulty_model_version": "3.0.0"
}
```

Per catene e Nested, si può adottare una crescita a soglie ispirata al codice SE. `ChainingHint.getLengthDifficulty()` aumenta il rating di 0.1 quando la complessità supera soglie geometriche approssimativamente pari a 4, 6, 8, 12, 16, 24 e così via; la complessità totale comprende anche le sottocatene. citeturn12view0

Una formula implementabile è:

```python
CHAIN_THRESHOLDS = (
    4, 6, 8, 12, 16, 24, 32, 48,
    64, 96, 128, 192, 256, 384, 512,
)


def chain_length_extra(complexity: int) -> float:
    return 0.1 * sum(
        complexity > threshold
        for threshold in CHAIN_THRESHOLDS
    )


def nested_extra(metrics: dict[str, float]) -> float:
    depth = max(int(metrics.get("nested_depth", 0)), 0)
    subproofs = max(int(metrics.get("nested_subproof_count", 0)), 0)
    branches = max(int(metrics.get("branch_count", 0)), 0)

    return (
        0.20 * max(depth - 1, 0)
        + 0.10 * math.log2(1 + subproofs)
        + 0.08 * math.log2(1 + branches)
    )
```

Per i fish:

```python
def fish_extra(metrics):
    return (
        0.10 * max(metrics["fish_size"] - 2, 0)
        + 0.05 * metrics["fin_count"]
        + 0.10 * metrics["endo_fin_count"]
        + 0.10 * metrics["cannibalistic_count"]
```

Questi extra non devono modificare la categoria canonica. Un Finned Swordfish resta un Finned Swordfish anche se la sua prova concreta è più costosa di un Franken Fish semplice.

La ricalibrazione deve essere corpus-based:

| Fase | Procedura |
|---|---|
| Raccolta | Creare un corpus di stati con tecnica bersaglio certificata da HoDoKu, SE/SukakuExplainer e test manuali |
| Normalizzazione | Applicare tutte le isomorfie Sudoku per ridurre bias di coordinate e cifre |
| Verifica | Confrontare conclusioni, non soltanto nomi, tra i solver |
| Etichettatura | Registrare tecnica specifica, parent SE, rating esterno e complessità della prova |
| Separazione | Dividere per puzzle, non per singola mossa, in training, validation e holdout |
| Ordinamento | Raccogliere confronti pairwise: “questa prova è più difficile di quella” |
| Stima | Usare regressione isotona o ottimizzazione robusta con ancore SE fisse |
| Regolarizzazione | Penalizzare inversioni tra sottotipi parametrici, per esempio Swordfish più facile di X-Wing |
| Validazione | Misurare agreement sui nomi, errore assoluto del rating e stabilità sotto simmetrie |
| Benchmark | Registrare tempo, nodi espansi, cache hit e timeout per tecnica |
| Revisione | Ispezionare gli outlier, soprattutto uniqueness, ALS, nets e Nested |
| Versionamento | Pubblicare una nuova `DIFFICULTY_MODEL_VERSION` quando cambia un valore o una formula |

Una funzione obiettivo possibile è:

```text
loss =
    errore assoluto rispetto alle ancore esterne
  + penalità per inversioni pairwise
  + penalità di non monotonicità familiare
  + penalità per instabilità sotto isomorfie
```

Non bisogna addestrare il rating sul tempo di esecuzione puro. Il costo computazionale dipende dall’implementazione, mentre la difficoltà tecnica dovrebbe riflettere soprattutto la struttura della prova.

## Puzzle di riferimento e strategia di test

Il test più affidabile per un detector non è un puzzle intero, ma uno **stato di candidati minimo**. Un puzzle può contenere contemporaneamente molte tecniche più semplici, può cambiare percorso dopo una mossa e può essere classificato diversamente da solver differenti. Ogni entry del catalogo dovrebbe quindi avere almeno:

```python
@dataclass(frozen=True)

    name: str
    technique_id: str
    candidates: dict[tuple[int, int], frozenset[int]]
    solved_values: dict[tuple[int, int], int]

    expected_eliminations: frozenset[Candidate]
    forbidden_technique_ids: frozenset[str]
```

| Regression | Identico esito logico sul corpus congelato, salvo cambi documentati di classificazione |
| Performance | Budget distinto per local, chain, ALS, nested e complete tree |

## Piano incrementale di migrazione

La migrazione consigliata comprende sedici patch piccole, ciascuna integrabile e reversibile.

Le correzioni concrete da applicare subito nella pipeline sono:

```python
def normalize_proof_metrics(logic: dict) -> dict:
    explicit = dict(logic.get("metrics") or {})
    derived = derive_metrics_from_proof(logic)

    # Compatibilità con vecchi record.
    if "nested_depth" not in explicit:
        explicit["nested_depth"] = max(
            number(explicit.get("nesting_depth")),
            number(explicit.get("max_depth")),
        )

    metrics = dict(derived)

    # Le metriche esplicite del motore hanno precedenza.
    for key, value in explicit.items():
        if key in metrics and isinstance(value, (int, float)):
            metrics[key] = max(metrics[key], value)
        else:
            metrics[key] = value

    metrics["metrics_version"] = "2.0.0"
    return metrics
```

`techniques.py` non deve più eseguire:

```python
proof["metrics"] = _proof_metrics(deduction)
```

se `_proof_metrics()` considera soltanto le catene visualizzate. Deve invece fare:

```python
proof["metrics"] = normalize_proof_metrics(proof)
```

Il solver deve poi leggere unicamente le metriche normalizzate:

```python
metrics = move["logic"]["metrics"]

node_count = metrics["node_count"]
branch_count = metrics["branch_count"]
nested_depth = metrics["nested_depth"]
nested_subproof_count = metrics["nested_subproof_count"]
```
